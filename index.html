왜 지금인가 — 국외 사례

데이터·CRM은 이미 AI가 굴립니다

Salesforce Einstein — 리드 스코어링

부동산 CRM에서 리드를 60초 내 1~99점으로 채점해 우수 리드를 자동 배정. 깨끗한 데이터 + 과거 계약 200건 이상이면 정확도 75~85%, 전환율 최대 +30% 향상을 제시합니다.

CBRE · JLL — 문서 자동화

CBRE는 ML로 임대 처리 수작업을 25% 감소. JLL은 'JLL GPT'로 임대차 계약서를 자동 요약·분류하고 포트폴리오 대시보드를 대화로 전환합니다.

Claude Cowork — 문서·데이터 워크플로

대용량 컨텍스트로 계약서 전체를 읽고, 커넥터(MCP)로 내부 DB·문서관리 시스템을 권한·로깅과 함께 연결해 멀티스텝 업무를 수행합니다.

AIG — 문서 판독 정확도

Claude 도입 후 서류 검토 5배+ 단축, 데이터 정확도 75%→90%+. 사람 검증과 함께 끌어올린 것이 핵심 — 트랙 2 문서 판독의 방향입니다.

출처: Salesforce/Einstein 자료·업계 분석 · CBRE · JLL Newsroom · Anthropic(anthropic.com/news). 수치는 각 사 발표·보도 기준이며 조건에 따라 달라질 수 있습니다.

직방 — 데이터 인프라화

전국 단지·세대 단위 구조화 데이터 + 가격 예측 모델 + 탐색 데이터를 축적. 'AI중개사'를 전 주거유형으로 확장하며 "검색 플랫폼에서 AI 의사결정 인프라로" 전환을 표방합니다. 데이터 구조화가 곧 경쟁력임을 보여줍니다.

밸류맵 — 자동 가치평가

AVM(자동가치평가모형)으로 토지·빌딩·상가를 산정하고, 담보채권 평가 자동화(ABR)로 확장. 정형화된 데이터가 쌓이면 사람 감정평가에 근접하는 결과가 가능합니다.

다방 · 리치고 · 부동산플래닛

매물 AI 설명, AI 시세·지역 분석 등 프롭테크사의 데이터 서비스 경쟁이 가속. 모두 깨끗하게 구조화된 데이터가 출발점입니다.

공공데이터 개방

국토부 실거래가, 한국부동산원 통계, 공공데이터포털 OpenAPI — 내부 CRM과 결합하면 "우리 분양가가 시세 대비 어디인지"를 답할 수 있습니다.

출처: 인공지능신문·한국금융신문·헤럴드경제·딜사이트 보도, DBpia 논문. 서비스 명칭·수치는 보도 시점 기준입니다.

토큰 (Token)

AI가 텍스트를 처리하는 기본 단위. 단어 하나일 수도, 더 작은 조각일 수도 있습니다. (영어 1단어 ≈ 1~2토큰, 한글은 더 잘게 쪼개집니다)

컨텍스트 (Context)

AI가 지금 대화에서 참고하는 정보의 범위. "아까 그거"라고만 해도 알아듣는 이유입니다.

첨부한 파일, 마운트한 폴더, 연결한 도구가 모두 컨텍스트에 들어갑니다.
컨텍스트 윈도우

모델이 답을 만들 때 한 번에 볼 수 있는 정보 상자의 크기. 단위는 토큰입니다.

100만토큰 ≈ 소설 9~10권

비어 있는 새 대화도 시스템 프롬프트 등으로 이미 수만 토큰을 씁니다.

한 줄 정리: 토큰 = 처리·비용의 단위, 컨텍스트 = AI가 참고하는 정보 범위, 컨텍스트 윈도우 = 그 정보가 들어가는 상자의 크기.

좋은 프롬프트는 무엇이 다른가

나쁜 예 → 좋은 예

✕ "이 고객 명단 중복 좀 정리해줘"

[맥락] 첨부 CSV는 분양 상담 고객 명단이다. 동일인이 여러 행에 있고 표기가 제각각이다. [규칙 — 애매한 경우 이렇게] - 동일인 판단: 이름 + 연락처 숫자만 - 중복이면 가장 최근 행을 남기고 병합 - 값이 비면 빈칸으로, 추정하지 말 것 [출력] - 정리된 표 + 이상치는 별도 시트로 분리 - 처리 로그: 원본 N행 → 결과 M행, 병합 건수, 판단이 애매했던 행 목록
좋은 프롬프트의 4요소
  • 맥락 (What data) — 이 데이터가 무엇인지
    → 1행이 무엇인지부터 알려주기
  • 규칙 (Rules) — 애매할 때의 판단 기준
    → 중복 판단 기준을 내가 정해서 준다
  • 처리 로그 (Log) — 무엇을 어떻게 바꿨는지
    → 데이터가 조용히 사라지는 걸 막는다
  • 출력 형식 (How) — 표·분리·형식
    → 바로 쓸 수 있는 결과
핵심: "알아서 정리해줘"라고 하면 AI가 자기 기준으로 지웁니다. 판단 기준을 내가 주는 것이 데이터 작업의 승부처입니다.

데이터베이스 & Supabase

데이터베이스 = 사라지지 않는 엑셀

엑셀은 파일(내 컴퓨터에만, 동시 편집 시 충돌). 데이터베이스는 서버의 표 — 여러 사람이 동시에 쓰고, 새로고침해도 남아 있습니다.

테이블 = 시트, 행(row) = 한 건, 열(column) = 항목

Supabase

설치 없이 클라우드에서 바로 쓰는 데이터베이스. 무료 티어가 있고, Claude 공식 커넥터가 있어 대화로 조작할 수 있습니다.

키(Key) — 표를 잇는 축

기본키(Primary Key) = 그 표의 고유번호. 외래키(Foreign Key) = 다른 표를 가리키는 값.

customers(id, 이름, 연락처, 등급) consultations(id, customer_id, 일시, 내용) ↑ 외래키로 고객과 연결

고객ID 하나로 상담·계약·광고 유입까지 이어져야 "이 채널 고객이 실제 계약했나"를 답할 수 있습니다.

왜 표를 나누나: 고객 1명에 상담 5건이면 한 표에 넣을 때 이름·연락처가 5번 반복됩니다. 나누면 한 곳만 고치면 됩니다. 2회차에 테이블 5개를 이렇게 설계합니다.

내가 안 눌러도 도는 4가지

스케줄 태스크

라이브 아티팩트

연결된 데이터로 스스로 갱신되는 결과물. 고객 현황·계약 KPI를 한 번 만들어두면 매번 다시 묻지 않아도 최신 상태로 유지됩니다.

파일을 매번 올리지 않고 원천 시스템을 직접 읽기. Supabase·Airtable·Gmail·Google 등. 항상 최신 데이터로 작업하고, 권한을 주면 되쓰기(상태 갱신)도 가능합니다.

AI가 못 읽는 표는 사람도 결국 못 씁니다.

첨부한 고객 명단 엑셀을 정리해줘. [1] 중복 제거 동일인 판단 기준: 이름 + 연락처 숫자만 남긴 값 - 중복이면 가장 최근 행을 남기고 병합 - 병합 시 비어있던 칸은 다른 행 값으로 채움 [2] 표기 통일 - 연락처: 숫자만 (하이픈·공백 제거) - 거주지역: 시·군·구 레벨로 통일 (예: 경기 화성시 / 서울 강남구) 판단이 안 되면 원본 유지하고 '검토필요' 표시 - 이름: 뒤에 붙은 "님/씨/고객님" 제거 [3] 등급 값 표준화 등급 컬럼의 값이 제각각이다 (계약가능 / 계약 가능 / A / 상 …). 아래 4개 중 하나로 통일: 계약가능 / 재상담 / 휴면 / 이탈 - 어떤 원본 값을 어디에 매핑했는지 매핑 표를 함께 출력 - 판단이 안 되는 값은 임의로 정하지 말고 목록으로 보고 [4] 이상치 탐지 - 연락처 자릿수가 맞지 않는 행 - 날짜가 미래이거나 형식이 깨진 행 - 예산이 비정상적으로 크거나 작은 행 → 삭제하지 말고 별도 시트로 분리 [5] 처리 로그 원본 N행 → 결과 M행. 병합 건수, 이상치 건수, 판단이 애매했던 행 목록

부동산 실무에서 가장 시간을 많이 잡아먹는 작업이 여기서 사라집니다.

프롬프트
첨부한 건축물대장(가상 샘플)에서 아래 항목만 JSON으로 추출해줘. { "소재지": "", "대지면적_㎡": null, "연면적_㎡": null, "건폐율_퍼센트": null, "용적률_퍼센트": null, "주용도": "", "층수_지상": null, "층수_지하": null, "사용승인일": "YYYY-MM-DD", "주차대수": null, "판독불가항목": [], "확인필요항목": [] } 규칙: - 숫자는 단위를 제거한 숫자만 넣을 것 - 원문에서 읽을 수 없으면 null, 그 항목명을 "판독불가항목"에 넣을 것 - 추정해서 채우지 말 것 - 글자가 흐릿하거나 겹쳐서 확신이 낮은 항목은 "확인필요항목"에 넣을 것
JSON이 뭔가요?

이름표가 붙은 데이터입니다. 표는 사람이 보기 좋고, JSON은 프로그램이 받기 좋습니다.

{ "대지면적_㎡": 1250.5, "용적률_퍼센트": 249.8 }

2회차에 이 JSON이 그대로 데이터베이스에 들어갑니다. 그래서 지금 JSON으로 받는 연습을 합니다.

금액 · 면적 · 날짜 오독은 곧바로 실무 리스크입니다
자동 입력 전에 사람이 확인하는 절차가 반드시 있어야 합니다.
① 표본 검증
추출 항목 중 3개를 무작위로 골라 원문과 대조. 1개라도 틀리면 전부 다시 봅니다.
② 논리 검증
연면적 ÷ 대지면적 ≈ 용적률이 맞는지. 서로 계산되는 값끼리 앞뒤가 맞는지 확인합니다.
③ 자백 확인
"판독불가"·"확인필요" 목록을 먼저 봅니다. AI가 스스로 자신 없다고 한 곳이 실제로 틀릴 확률이 가장 높습니다.
검증을 프롬프트에 내장하는 법
방금 추출한 JSON을 스스로 검증해줘. 1. 연면적 ÷ 대지면적으로 용적률을 역산해 추출값과 비교 2. 각 항목마다 확신도(상/중/하)를 표시 3. 확신도 "하"인 항목은 원문의 어느 부분을 근거로 했는지 인용 4. 단위(㎡/평, 원/만원)가 섞인 곳이 있는지

실습 3  CRM 데이터 분석·시각화

프롬프트 — 자동 분류
첨부한 상담 이력 데이터를 근거로 고객을 자동 분류하고 액션 리스트를 만들어줘. [분류 기준 — 내가 정한다] - 계약가능: 최근 30일 내 상담 2회 이상 + 구체적 호실 언급 - 재상담필요: 상담은 있으나 60일 이상 무접촉 - 휴면: 90일 이상 무접촉 - 이탈: 타 단지 계약 등 명시적 거절 [출력] 1. 분류별 인원수 요약 2. 고객별 표: 고객ID / 분류 / 근거 / 마지막 접촉일 / 권장 다음 액션 3. "계약가능" 고객은 우선순위 순으로 정렬 4. 분류가 애매했던 건은 별도 표시
기준을 내가 준다는 게 핵심. "알아서 분류해줘"라고 하면 AI 마음대로 나눕니다. 우리 회사 기준을 명시해야 실무에 쓸 수 있습니다.
위 기준을 그대로 쓰지 말고 먼저 따져보세요. 31일째 무접촉 고객은 어느 분류에 들어갑니까? 60~90일은 재상담과 휴면 양쪽에 해당합니다. 규칙의 구멍을 메우는 것까지가 이 실습입니다.
프롬프트 — 차트 자동 생성
위 결과와 광고 집행 데이터를 함께 보고 아래 차트를 만들어줘. 라이브 아티팩트로. 1. 월별 상담 건수 + 계약 건수 (이중 막대) 2. 유입 채널별 리드 수와 계약 전환율 (막대+선) 3. 채널별 계약 1건당 광고비 (막대, 낮은 순) 4. 고객 분류 비중 (도넛) 각 차트 아래에 "이 그래프가 말하는 것"을 한 문장으로. 숫자 근거를 포함해서.
3번이 실무에서 가장 강력합니다

"계약 1건당 광고비"는 대부분의 현장에서 계산해 본 적이 없는 숫자입니다. 채널별로 몇 배씩 차이가 나는 경우가 흔하고, 그걸 아는 순간 예산 배분이 바뀝니다.

차트도 검증 대상입니다. 막대 하나를 골라 원본 데이터에서 직접 세어 보세요. 시각화는 틀려도 그럴듯해 보입니다.

실습 3-2  실거래가로 시세 비교

프롬프트 — 시세 대비 분양가
첨부한 실거래가 자료를 전용면적 구간별로 정리하고, 같은 면적대의 우리 분양세대 분양가와 비교해줘. [먼저 확인할 것] 실거래가는 전용면적 기준, 우리 분양세대표에는 전용·공급면적이 둘 다 있다. 어느 쪽으로 맞춰야 같은 것끼리 비교되는지 먼저 알려주고 진행할 것. [출력] 1. 단지별 · 면적별 평균 거래가 2. 우리 분양가가 인근 시세 대비 어느 위치인지 3. 영업에서 쓸 수 있는 비교 문구 3개 숫자마다 어느 행에서 나왔는지 출처 표시.
B직군의 핵심 역량이 여기 있습니다. 공시가·실거래가 같은 외부 데이터를 우리 데이터와 연결할 수 있는가 — 그 판단이 곧 데이터 구조 이해입니다.
전용 vs 공급 — 가장 흔한 오류

국토부 실거래가는 전용면적으로 공개되고, 분양 현장은 공급면적(평형)으로 말합니다. 이걸 섞어서 비교하면 30% 이상 어긋납니다.

AI가 이 차이를 먼저 짚어내는지 보세요. 그냥 비교해 버리면 그 결과는 버려야 합니다.

이어서 시킬 것
고객 데이터의 거주지역별로 계약률에 차이가 있는지 보여줘. 어느 지역에서 온 고객이 실제로 계약까지 가는지 알면 다음 광고를 어디에 뿌릴지 정해진다.
실거래가 API 연동은 심화 과제입니다. 오늘은 CSV로 원리를 익히고, 인증키 발급 후 OpenAPI 연동은 온라인 과제와 3회차 시연으로 이어집니다.

[화면 3 · 상담 이력] - 고객 상세 하단에 상담 목록 (최신순) - 상담 추가 폼: 일시 · 채널 · 담당자 · 내용 · 다음액션 - 상담 추가 시 고객의 최근상담일 자동 갱신 [공통 UI] - 상단 탭: 고객 / 대시보드 - 로딩 중 · 데이터 없음 상태를 명확히 표시 - 에러 발생 시 사용자에게 한국어 메시지 - 모바일에서 표가 가로 스크롤되게 [보안] - service_role 키를 사용하지 말 것 - 코드에 키를 하드코딩하지 말 것 - 삭제는 soft delete(deleted_at 표시)로 [검증 편의] - "샘플 데이터 넣기" 버튼: 가상 고객 10명 + 상담 20건을 한 번에 생성 - "전체 삭제" 버튼 (확인 2번) [하지 말 것] - 실제 개인정보를 샘플로 생성하지 말 것 (이름은 "고객A", 연락처는 010-0000-0001 형태)
생성 직후 반드시: "샘플 데이터 넣기" → 새로고침(F5) → 데이터가 남아 있는지 확인. 사라지면 Supabase에 실제로 저장되지 않은 것입니다.
APPENDIX 4

Supabase 스키마 SQL

Supabase → SQL Editor → 새 쿼리 → 아래를 붙여넣고 Run. 테이블 5개 · 대시보드용 뷰 4개 · 보안 규칙이 한 번에 생성됩니다. LMS의 01_schema.sql 전문을 그대로 붙여넣으세요 — 아래는 요약입니다.
-- 1. 고객 create table customers ( id bigserial primary key, name text not null, phone text, region text, -- 거주지역 (시·군·구) source text, -- 유입경로 interest_type text, -- 관심타입 budget bigint, grade text, -- 계약가능/재상담/휴면/이탈 contract_status text default '미계약', last_consulted_at date, deleted_at timestamptz, -- soft delete created_at timestamptz default now() ); -- 2. 분양 세대 create table units ( id bigserial primary key, dong text, ho text, unit_type text, -- 84A 등 area_exclusive numeric, -- 전용 ㎡ (실거래가 기준) area_supply numeric, -- 공급 ㎡ (분양가 기준) floor int, direction text, -- 향 (남향 등) price bigint, status text default '미분양', created_at timestamptz default now() );
-- 3. 상담 create table consultations ( id bigserial primary key, customer_id bigint references customers(id) on delete cascade, consulted_at timestamptz not null, channel text, staff text, content text, next_action text, deleted_at timestamptz, created_at timestamptz default now() );
references 가 하는 일

customer_id bigint references customers(id) 는 "이 값은 반드시 고객 표에 있는 id여야 한다"는 약속입니다. 없는 고객의 상담이 들어갈 수 없게 막아줍니다.

on delete cascade 는 고객을 지우면 그 고객의 상담도 함께 지운다는 뜻입니다.

컬럼명을 바꾸고 싶다면 지금 바꾸세요. 2회차 웹앱 프롬프트가 이 컬럼명을 그대로 씁니다. 나중에 바꾸면 코드와 DB가 어긋나 저장이 실패합니다. 다음 장에서 계약·광고 테이블과 보안 설정을 이어서 실행합니다. →
APPENDIX 4 (계속)

계약 · 광고 테이블 & 보안 설정

앞의 SQL에 이어서 실행
-- 4. 계약 create table contracts ( id bigserial primary key, customer_id bigint references customers(id), unit_id bigint references units(id), contracted_at date not null, amount bigint, status text default '계약', -- 판독 결과 검증 이력 verified_by text, verified_at timestamptz, deleted_at timestamptz, created_at timestamptz default now() ); -- 5. 광고 집행 create table ad_spend ( id bigserial primary key, channel text not null, spend_date date not null, cost bigint, impressions bigint, clicks bigint, leads int, created_at timestamptz default now() ); -- 조회 속도용 인덱스 create index on consultations(customer_id); create index on contracts(customer_id); create index on ad_spend(channel, spend_date); -- 보안: RLS 활성화 + 실습용 전체허용 정책 -- 5개 테이블 전부 — 하나라도 빠지면 조회가 0건이 됩니다 alter table customers enable row level security; alter table units enable row level security; alter table consultations enable row level security; alter table contracts enable row level security; alter table ad_spend enable row level security; create policy "lab_all" on customers for all using(true) with check(true); -- units · consultations · contracts · ad_spend 도 동일하게 -- (전문은 LMS의 01_schema.sql 참조)
인덱스가 하는 일

책의 색인과 같습니다. 없으면 매번 처음부터 다 훑고, 있으면 바로 찾아갑니다. 검색·필터 화면이 느려지면 그 컬럼에 인덱스를 추가하세요.

대시보드용 뷰 4개가 함께 만들어집니다

v_grade_summary 등급별 인원 · v_unit_status 세대 현황 · v_region_summary 상권 · v_channel_efficiency 채널별 계약 1건당 비용

실습 5에서 복잡한 조인 없이 뷰만 읽으면 대시보드가 완성됩니다.

시드 끝의 setval 5줄을 빠뜨리지 마세요. 정해진 id로 데이터를 넣으면 번호표가 1에 멈춰 있어, 웹앱에서 신규 고객을 등록하는 순간 오류가 납니다. 실습 중 가장 자주 나오는 에러입니다.
마지막 정책은 실습 전용입니다. using (true)는 키를 아는 누구나 전체 데이터에 접근할 수 있다는 뜻입니다. 그래서 이 실습에는 가상 데이터만 넣습니다.
실무로 가져갈 때 바꿔야 할 것
1
Supabase Auth로 로그인 붙이기이메일 로그인만으로도 충분합니다
2
정책을 로그인 기반으로 교체using (auth.uid() is not null)
3
담당자별 분리가 필요하면행에 owner_id를 두고 본인 것만 보이게
Claude Code에게 시키셔도 됩니다. "이 프로젝트에 Supabase 이메일 로그인을 붙이고, RLS 정책을 로그인한 사용자만 접근 가능하게 바꿔줘" — 3회차 개선 아이디어 항목으로 좋은 주제입니다.
APPENDIX 5

직군별 응용 프롬프트

B · 금융 · 투자

외부 데이터 수집·구조 이해

첨부한 실거래가 CSV의 구조를 설명하고, 우리 분양 세대 표와 연결하려면 어떤 컬럼을 어떻게 맞춰야 하는지 알려줘. 면적 기준(전용/공급)이 다르면 지적해줘.
C · 분양 · 중개세일즈

조건별 검색·필터링 설계

고객이 "84타입, 남향, 10층 이상, 6억 이하"를 원할 때 즉시 매칭되도록 검색 조건 설계를 제안해줘. 어떤 컬럼에 인덱스가 필요한지도.
D · 자산 · 운영

임차인·민원·유지보수 체계화

첨부한 민원 접수 대장을 구조화해줘. - 유형별 자동 분류 (누수/소음/시설/기타) - 반복 민원(같은 호실·같은 유형) 표시 - 평균 처리 소요일과 지연 건 목록 - 유지보수 예산 배분에 참고할 요약
E · 디지털 · 고객관리 · 마케팅

리드 수집·고객 접점 통합

채널이 다른 리드 데이터 3종 (홈페이지 / 광고 / 전화)을 하나로 통합해줘. - 컬럼명이 달라도 같은 의미면 매핑 - 채널 간 중복 고객을 찾아 표시 - 통합 후 채널별 계약 전환율 비교 - 매핑 규칙을 표로 남겨줘 (다음에 재사용)
